# 把消耗、上下文和预算分别算清楚

一段回答背后可能有几个模型请求：模型先查文件，继续调用工具，再生成最终回答；中途还可能压缩一次旧历史。屏幕上看见一条回答，不代表只发生了一次请求。Token 系统从这些实际请求记账，而不是从聊天气泡猜消耗。

这次设计有一个明确前提：**不依赖 tokenizer，也不要求供应商提供额外的计数接口。**实际消耗只信供应商上报的 usage；上下文使用最近可靠的输入用量校准，再保守估算新增内容。估算用于决定何时整理上下文，不能补进历史消耗。

## 三个数字，各回答一个问题

| 名称 | 回答的问题 | 数据来源 |
|---|---|---|
| 已上报用量 | 实际请求已经消耗了多少？ | Provider 的 usage 快照 |
| 当前上下文估算 | 下一次请求可能带多少 token？ | 最近有效输入 usage + 新增内容估算，或全量粗估 |
| 请求预算 | 这次还能携带多少内容、预留多少输出？ | 模型窗口、实际输出上限和安全余量 |

例如，同一段 10K 历史被发送了五次，累计输入可能接近 50K；下一次请求的上下文仍可能只有 10K。缓存减少重复输入的处理成本，但缓存内容仍是模型这次请求看到的输入，不能从上下文占用里扣掉。

界面“详情”分别显示会话累计已上报用量和当前上下文估算。退出小结显示本次启动已上报用量。两者范围不同，字段含义和格式相同。

详情超过八行时在自己的视口内滚动，输入区保持可用；方向键、PageUp/PageDown、Home/End 或滚轮都能读到末尾。矮终端使用详情弹窗，Esc 返回保留的草稿。完整数据存在于消息对象里，并不保证用户真的看得到，因此布局测试也检查实际渲染与滚动。

上下文压缩在聊天中保留一条可展开活动，展示前后完整请求的估算和上下文减少比例。手动、自动及紧急压缩使用相同交互，恢复 Session 仍保留结果；内部重试更新同一活动，但每次真实摘要请求单独记账。详见 [看懂一次上下文压缩](context-compaction.md)。

## 一个请求，一份不断更新的记录

[`RunUsageTracker`](../../lancher_code/usage/ledger.py) 为每次实际调用生成请求 UUID。记录关联当前 Session、助手消息或轮次、用途、供应商协议和模型。正常对话与摘要请求走同一条观察路径；真正重发的请求取得新 UUID，不能把重试当成前一次请求的尾帧。

流式用量通常是累计快照：

```text
请求 A：输出 10 → 输出 25 → 输出 25
账本 A：输出 25

请求 B：输出 7
两个请求合计：输出 32
```

同一请求覆盖其已知字段，不累加每一帧；不同请求才相加。后来的帧只提供输出时，保留此前已上报的输入与缓存。这样既不会重复计数，也不会因为一个字段缺席就把它清成零。

请求内容与实际尝试的身份分开。同一个 `ChatRequest` 即使连续发送两次、甚至并发发送，也会在入口生成各自的局部副本和新 UUID；回调不会互相覆盖。统一入口与原生 Provider 通过一次性标记共用这次 UUID，避免一趟调用被记成两条请求。原请求对象上的 ID 只表示最近开始的一次尝试，完整归属以账本为准。

Provider 开始请求、收到快照和结束请求时分别报告事实。界面和消息更新不决定是否记账，因此摘要没有聊天气泡也会进入账本，异常或取消前收到的快照也不会丢失。

Session 将请求记录保存到自己的事件日志，恢复时重建会话累计。本次启动的账本从程序启动开始，只收这次真实发生的请求；恢复上周的对话不会让退出小结再加一次上周的消耗。

账本按请求增量保存：`usage.request_updated` 只携带这一条请求的最新快照，重复帧不会重复写入。阶段或上下文锚点变化的 `state.changed` 不再附带全部历史请求；否则第 100 次请求可能又写一次前 99 条，长会话日志会按平方膨胀。恢复时将未结束请求改为 `incomplete`，也追加这条请求的状态变化，已上报数字照样保留。

Checkpoint 保留完整账本，用空间换取较快的恢复：读取快照后只重放尾部事件。快照缺失时可以从完整日志得到同样结果，因此它是加速恢复的派生文件；缺失的是初始请求账本则必须拒绝恢复，不能假装旧消耗为零。

消息上的用量是请求账本的派生视图。即使用量事件已保存、聊天气泡还没来得及更新就崩溃，恢复时也会从账本重新汇总。当前上下文计量状态使用版本 `2`；缺少请求账本或仍使用旧计量状态的会话会明确拒绝恢复，原文件继续保留，避免把无法还原的历史消耗显示成已知零。

## 未知、真实零和部分上报

[`MessageUsage`](../../lancher_code/usage/models.py) 的数值字段允许 `None`：

| 情况 | 内部值 | 显示 |
|---|---|---|
| 供应商明确上报缓存读取为零 | `0` | `0 tokens` |
| 供应商没有提供缓存读取 | `None` | `--（未提供）` |
| 两次请求只有一次提供输入 | 已知输入之和，保留不完整标记 | `100 tokens（部分上报）` |
| 请求尚未得到最终用量 | 已知快照，`is_final=False` | 保留数字并说明未完整 |

假设请求 A 报告输入 100、输出 20，请求 B 只报告输出 30。已知总计是 150，但输入缺了一段，所以显示“150 tokens（部分上报）”。既不能抹掉已经知道的 150，也不能称它为本次完整消耗。

如果整个范围只有输入 100 已知、输出尚未提供，总计同样保留“100 tokens（部分上报）”；只有输入和输出都未知才显示总计 `--`。这里展示已知小计，没有把未知输出推算成零。

没有发出任何请求时，累计零是已知的；发出了请求却完全没有 usage 时，结果未知。取消、网络断开和请求失败也不能被解释为免费。

字段是否存在与流是否正常结束是两个维度。Claude 开始帧中的输出零只是早期快照；需要最终累计帧才能确认输出完成。OpenAI 兼容流缺少最终 usage 时，正常收到结束标记也不能凭空补齐数值。

## 缓存和推理都是子项

我们统一采用“输入包含缓存，输出包含推理”的口径：

```text
总计 = 输入 + 输出
缓存命中率 = 缓存读取 / 输入
```

Claude 的普通输入、缓存读取与缓存创建在协议中分开提供，适配层将它们合成为总输入；OpenAI 兼容协议通常直接提供总输入和缓存子项。适配完成后，后续代码只使用统一语义。

缓存创建是输入子项，和缓存命中不是一回事。推理量是输出子项，不能在输出之外再加一次。可选子项没有上报时，不根据其他字段倒推一个数字，也不强迫每个模型提供它。

命中率使用累计命中量除以累计输入量。输入 1,000、命中 900，再加输入 9,000、命中零，整体是 9%，不是两个百分比平均得到的 45%。只有必要字段完整、最终确认、请求正常结束且数值关系合理时才显示比例。

例如供应商报告输入 100、缓存读取 120，原始异常保留供排查，缓存比显示 `--（上报数据异常）`；把 120% 截成 100% 会掩盖协议问题。

## 最近有效 usage 为什么能校准

[`context/tokens.py`](../../lancher_code/context/tokens.py) 将请求拆成模型可见内容：system、消息正文、工具定义、工具参数、工具结果及消息包装开销。内部 metadata、空的数据类字段和外层 JSON 转义不作为模型正文计数。

第一份请求还没有真实用量可参考，只能粗估。Provider 返回可信输入后，记录“输入 token + 这次请求发出前的快照边界”。下一次请求如果保留同样的 system、工具与消息前缀，计算：

```text
下一次上下文估算 = 上次实际上报的输入 + 新增消息的保守估算
```

例如请求输入实际上报 1,000、回答输出 200。锚点是 1,000；回答被加入下一次请求后再估算这段新增内容。不能先把锚点写成 1,200，又把回答加一次，否则输出就重复计算了。

输入未知、输入仍是部分快照、数据异常或请求没有正常完成，都不能建立新的可靠锚点。后来的不完整请求也不会把更早仍然匹配的可靠锚点覆盖成一个小得离谱的数字。

估算结果明确分为“已校准估算”和“未校准估算”。校准仍不是下一次请求的真实 usage：新增文本、工具包装和供应商隐藏处理还有误差，需要留安全余量。

### 什么时候旧锚点失效

- 切换模型，不能沿用另一模型的计数特性。
- 修改 system、工具定义或请求形状，旧输入不再描述同一份前缀。
- 阶段、计划等动态提醒改变，或新用户轮次把提醒从旧消息移到最新消息，原请求前缀不再相同。
- 压缩、卸载或编辑历史，原消息前缀发生变化。
- 消息前缀截短或内容不再匹配，不能只看“消息条数差不多”。

失效后回到全量保守估算，等待下一份可信输入重新校准。消息摘要和输入边界一起校验，避免恢复后把旧数字套在新请求上。

因此，“最近有效”并不保证跨所有用户轮次一直有效。有动态提醒的阶段，新一轮可能重新粗估；连续工具请求在同一轮内更容易保持相同前缀并沿用锚点。没有提醒变化且模型、工具和前缀相同的请求仍可继续校准。界面只读估算使用状态副本，不会为了显示另一份工具集合清掉真实请求的锚点。

### 没有锚点时怎么估

粗估区分 ASCII 和非 ASCII 文本，并按内容类别加入包装开销；当前策略约为 ASCII 每 3 个字符、非 ASCII 每 1.5 个字符估 1 token。它是保守的容量管理策略，不是宣称任何模型使用这套编码。

更细的类别拆分让误差可以定位：是 system 很大、工具定义很多，还是工具日志占满了请求。以后调整系数只需修改估算策略，不需要修改消耗账本，更不会把估算改写成供应商实际消耗。

## 预算随窗口变化，输出预留必须真的发出去

[`context/budget.py`](../../lancher_code/context/budget.py) 根据上下文窗口、请求输出上限和安全余量生成预算。正常回答与摘要的实际请求都携带对应的输出上限，Provider 使用该上限构造请求；不能只在本地“预留 2K”，实际却允许生成 20K。

预算分别给出输入上限、自动整理阈值、近期历史规模以及单条和同批工具结果额度。8K 窗口也能得到正的有效预算，不会再被固定的 20K 摘要预留和 13K 余量减成负数。

以没有启用额外思考预算的 8,192 token 窗口为例，普通请求默认预留 1,024 输出和 256 安全余量，因此硬输入额度是 6,912，自动整理阈值是 6,230。近期完整历史组的预算是 1,728，单条工具结果整理目标是 864，同批及累计工具结果视图的整理目标是 2,304。预览的正文、包装、大小与文件路径都参与计数，已经落盘的预览也不能当作零成本。这些额度属于输入预算内部，不能再次加到窗口外。摘要请求使用自己的输出额度，完成后还要按普通请求的完整 system、工具与输出预留重新检查。

Claude 启用思考时，容量管理和协议发送共享同一个思考预算默认值；实际输出上限同时容纳思考和回答余量。显式预算已经大于窗口时，输入额度会归零并给出错误，不能为了让数字好看而偷偷缩小服务端上限。

显式输出额度必须保留实发数值。若它本身已占满窗口，输入额度归零并在发送前拒绝，不为了得到好看的正预算偷偷缩小输出。

发送前重新检查当前请求。系统提示或工具定义本身已超过预算时，需要明确失败原因，不能无限压缩已经很短的历史。供应商仍可能报告真实超限，这时按紧急流程整理并限制重试次数。

## 大输出放回文件，压缩先验证再替换

超出整理额度的工具完整输出保存到当前 Session 的 `blobs/`，请求携带预览、大小和可再次读取的文件路径。额度足够时，预览优先保留开头与结尾，让启动信息和最后的错误都能被看到；需要中间内容时调用工具读原文。

额度按当前窗口计算，同批结果与多轮累计结果还有总额度，不能让十条分别未超限的日志合起来挤满请求。选择落盘对象时比较原文与完整预览的实际估算差额，连同既有预览一起检查目标。例如 8K 窗口中的十条 2,500 字符 ASCII 结果，会继续整理到包含预览成本的总量达到目标，而不是先卸载八条后忘记那八份预览。写文件失败时保留原内容，不能留下一个指向不存在文件的占位符。

大量文件路径与必要来源信息本身也可能超过整理目标；这时只保留最小引用，保留工具调用和结果配对，再由完整请求硬预算检查决定是否需要压缩或明确拒绝。整理目标不保证任意数量的结果都能放下。

摘要在候选上下文上生成，先确认请求正常结束、没有撞到输出上限、没有工具调用，摘要标签和九个章节有效，再检查候选是否真正变小、是否适合继续请求。未完成的工具调用禁止压缩。近期历史按完整轮次组保留，工具调用和结果不切成半对；整组过大时交给摘要，最新用户原话仍明确保留。补回原话后仍放不下，就拒绝候选。

候选保留的近期工具结果先按调用 ID 恢复为压缩前原文，再构建新的请求预览进行完整预算验证；摘要正文保持不变。这样重复构建请求和再次压缩都不会给预览再套一层包装，原始大小始终对应完整内容。验证全部通过后才原子替换当前模型上下文；完整事件历史仍保留。空摘要、截断摘要、变大的摘要、取消或异常，都不会先破坏正在使用的旧上下文。摘要请求即使最终验证失败，实际已经发生的消耗仍记到账本。

## 为什么参考这些实现，而没有照搬

- [Pi 的上下文管理](https://github.com/earendil-works/pi/blob/42a3497d03ad17e308a2299fa824727894f2c0ec/packages/coding-agent/src/core/compaction/compaction.ts)：最近有效 usage 与新增消息估算提供了校准思路。我们将锚点固定到请求输入快照，避免输出再次加入产生重复。
- [Codex 的内容估算](https://github.com/openai/codex/blob/main/codex-rs/core/src/context_manager/history.rs)：只计模型可见内容的方向值得参考。我们按自身支持的协议结构拆分内容，并使用统一保守策略。
- [OpenCode 的窗口预算](https://github.com/anomalyco/opencode/blob/055d95bb7e278c94baf06235a52cac79dd13ba67/packages/opencode/src/session/overflow.ts)：窗口和输出应共同决定输入额度。我们的预算同时覆盖工具预览和摘要后的恢复内容。
- [Gemini CLI 的压缩验证](https://github.com/google-gemini/gemini-cli/blob/9b6e0265d16bbd29ca51e33c9e0c01dc4cec5e83/packages/core/src/context/chatCompressionService.ts)：拒绝无效或没有变小的压缩，保留可用状态。我们将验证结果与持久化替换分开，并独立记录摘要消耗。

这些链接用于解释设计参考，不是运行依赖。LanCher 不下载模型 tokenizer，不需要额外付费计数请求，也不假定第三方项目的字段语义与自己相同。

## 继续开发时该守住什么

计数测试应检查真实语义：同一请求多帧不重复，只有输出不能校准输入，未知不能变零，缓存不能重复加，摘要和失败请求不能漏记，恢复不能污染本次启动。

上下文测试应覆盖中文、代码、JSON、工具定义和长日志；检查模型切换与历史变更使锚点失效，检查小窗口仍有有效预算，检查摘要被截断或变大时原投影仍可用。界面测试还要检查详情与退出使用同一套未知、部分上报和异常比例文案。

只有状态栏数字好看，不能证明计数正确。真实供应商 usage 是消耗依据，离线协议模拟用于验证边界；没有供应商实测时，应清楚报告验证范围。
