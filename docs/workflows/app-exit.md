# 结束这次工作，再把对话接回来

关掉终端助手时，有几件小事应该交代清楚：刚才是哪一段对话，下次怎么回来，这次实际用了多少模型 token，以及还在运行的服务会怎样结束。退出提示把这些信息留在普通终端里，方便复制和回看。

例如，一次用量完整的退出小结可以读成这样：

```text
今天也辛苦啦，LanCher 先下班咯～下次见 (｡･ω･｡)ﾉ

对话：启动一个 HTTP 小服务
下次在这个项目启动 LanCher Code 后，输入（项目：D:\项目目录）：
/session resume 99afd728580d4245871562151eef5259

本次启动已上报用量
输入：12,340 tokens
输出：2,156 tokens
缓存命中：8,000 tokens
总计：14,496 tokens
缓存比：64.8%
```

这里的恢复命令是在 LanCher Code 输入区执行的命令。先回到原项目目录启动程序，再粘贴这一行；它不是启动程序时的 CLI 参数。

## 标题负责让人认出来，UUID 负责准确找到

`/session resume` 的补全候选同时展示标题与 UUID。标题可以是“调查登录失败”或“整理工具调度器”，不用靠记住一串字符区分对话。默认标题来自第一条消息，也可以用 `/session rename <完整 UUID> <新标题>` 修改。

标题允许重复，重命名也不会改变对话身份。选择补全候选时，命令仍填入完整的 32 位 UUID；退出提示同样保留完整 UUID，避免显示得漂亮却无法恢复。同样标题的两段对话仍是两段对话，恢复逻辑始终按 UUID 定位。

窄屏的补全标题提示只占一行，过长部分裁短，完整 UUID 仍然保留。要阅读完整标题可用 `/session list`，不用为了容纳一条很长的标题把整个菜单和输入区撑开。

小终端进入退出确认时，暂时收起补全菜单和命令提示，为退出提醒、草稿和底部状态栏留出位置。候选选择与草稿没有清空；继续操作或确认超时后，菜单按原状态恢复。

补全与暂停队列同时存在时，先给完整恢复 UUID 留出高度；队列可缩到标题行，内容在自己的视口中滚动。输入区和底部操作不会因为两块辅助面板同时展开而被挤到屏幕外。

只启动程序、查看列表或打开新草稿，不会创建空 Session。退出优先提示当前对话；如果最后切到 `/session new` 的空白草稿，回退到本次最近实际使用且仍存在的对话。最近使用的对话已被删除时继续回退，全部删除后就没有恢复目标。仅启动后直接退出，不会从磁盘旧历史随便选一段。

还没发第一条消息的草稿本身没有恢复命令；告别也不会为了生成一个编号而创建 Session。详见 [Session 生命周期](session-lifecycle.md)。

## Ctrl+C 先辨认你是在停止，还是准备离开

工作中按 Ctrl+C，通常只是想让模型停一下，好换个说法或看看发生了什么。空闲时按 Ctrl+C，才进入退出确认。

| 此刻正在做什么 | 按 Ctrl+C 后发生什么 |
|---|---|
| 模型回答、工具执行、等待审批 | 停止本轮，暂停队列，保留草稿 |
| 手动压缩上下文 | 取消这次压缩操作 |
| 上一次停止还在收尾 | 提示正在停止，不再次取消清理任务 |
| 已经空闲 | 提示“再按一次 Ctrl+C 退出”，保留 3 秒确认窗口 |
| 3 秒内再次按下 | 确认退出，开始统一收尾 |
| 超时，或继续输入、点击、滚动页面 | 取消退出确认，下一次 Ctrl+C 重新提示 |
| 已经开始退出 | 不重复启动退出，也不跳过清理 |

所以从正在工作的状态离开，需要先停止工作；等它停稳，再空闲双按退出。用于停止工作的那次 Ctrl+C 不会偷偷算成“已经确认过一次退出”。`/exit` 已经明确表达离开意图，按命令直接退出。

Ctrl+D 不再作为状态详情快捷键。需要查看模型、用量和连接状态时，使用 `/status` 或输入区的“详情”按钮。

### 为什么确认计时不用墙上时钟

系统日期可能被校准、用户调整，甚至倒退。退出确认只关心“过去了多少秒”，因此 [`ExitFlow`](../../lancher_code/tui/exit_flow.py) 使用单调时钟。界面定时器负责显示和撤下提示，是否仍在 3 秒窗口内由状态机自己判断；即使界面某一帧刷新迟了，也不能让过期确认继续有效。

状态机只决定动作：取消工作、等待收尾、提示确认、退出或忽略。真正的异步取消和提示由界面执行。这样测试可以注入一个可推进的时钟，准确检查“2.9 秒还有效，3 秒整已过期”，不需要真的等待，也不靠抢到某一帧才能通过。

另一处刻意的约束是，发出停止意图以后会锁存它。连续按键只等待已开始的收尾，不会把清理任务再次取消。普通输入可以撤下退出确认，却不能把正在停止的工作变成“从来没停止过”。

## 先收尾，告别才说得准

退出不是清掉一张聊天界面。开发服务器、正在读写的管道、Session 的事件写入者和 MCP 连接，都需要完成自己的关闭。

顺序是：

1. 停止当前工作并等待收尾，关闭应用托管的全部进程。
2. 刷新 Session 记录、写入快照并释放写入锁，关闭 MCP 连接。
3. 取得最终的本次启动用量快照，以及仍可恢复的对话信息。
4. 回到普通终端后打印一次告别、恢复命令与用量小结。

告别不在界面卸载回调里打印。全屏终端界面还可能正在恢复屏幕，过早输出会被覆盖，也可能和清理日志挤在一起。清理结束后打印，信息才能留在正常终端里。

同样不能只检查界面上的“正在回复”。手动压缩有自己的操作任务，停止整个 Session 也可能仍在等待后台进程关闭。界面需要跟踪这些任务的真实结束，避免把“模型这轮没有在运行”误当成“所有工作已经结束”。

手动压缩交给独立 worker。主界面如果在处理 `/compact` 命令时一直等待模型返回，就腾不出消息循环接收 Ctrl+C；看上去有停止快捷键，实际上按键还排在长请求后面。让命令先返回、压缩在 worker 中继续，停止按键才有机会及时到达。

另一个容易遗漏的窗口是“任务已经排入，但协程还没有开始”。这时取消 worker，协程内的 `finally` 根本不会运行，界面可能一直停留在忙碌状态。实现分别检查压缩是否真正开始：已经开始就等待它自己的收尾，还没开始则直接恢复输入状态。Runner 也持有真实压缩任务，整个应用关闭时会等待它停止。

关闭步骤失败时，程序报告真实错误，并继续处理仍可独立关闭的资源。失败的小结不能宣称“已经保存完毕”或“所有进程都结束了”。已经开始的退出也不会因为又按一次 Ctrl+C 就重新从头取消：重复取消不是修复关闭失败的方法。

## 本次启动的账本，为何独立于 Session

退出时的“本次使用”从这次启动程序开始累计。切换三个 Session、换两个模型，或者恢复一段旧对话，都继续记在同一个 [`RunUsageTracker`](../../lancher_code/usage/ledger.py) 中。恢复前几天的 Session 不会把前几天的消耗再算一遍。

这个账本观察实际模型请求，而不是累加界面上的助手消息。一条回答可能经过多个工具循环，也可能先触发自动压缩；手动 `/compact` 同样调用模型。只统计聊天消息，会漏掉这些实际请求。

每个请求有独立 UUID。不同请求的用量相加，同一个流式请求的多次 usage 上报则覆盖该请求的累计快照。假设它先报告输出 10 token，后来报告累计 25 token，账本记 25，不是 35；最后一帧再次报告 25，也不会变成 60。

请求事实同时写入所属 Session 日志，用于恢复会话累计；本次应用进程的账本只收集这次真实发生的请求。两者使用同一个聚合逻辑，区别在记录范围。会话详情与退出小结也共享显示格式，未知字段、部分上报和异常比例不会各说各话。更完整的校准与预算说明见 [Token 与上下文](token-accounting.md)。

### 输入、缓存与总量怎么算

输入量已经包含缓存输入。OpenAI 的输入字段使用协议给出的总输入；Claude 的总输入由普通输入、缓存读取和缓存创建相加，缓存命中单独取缓存读取量。

```text
总 token = 输入 token + 输出 token
缓存命中率 = 缓存命中 token / 输入 token
```

缓存命中是输入的一部分，不能再加到总 token 上。缓存创建也不等于缓存命中；这次把内容写进缓存，不代表本次已经从缓存读到了它。提供方有上报时，显示“缓存创建（输入子项）”和“推理（输出子项）”；两个子项都不再次加入总计。

整个启动的命中率使用累计命中量除以累计输入量，不对各请求的百分比取平均。输入 1,000、命中 900 的请求，加上输入 9,000、命中 0 的请求，整体是 `900 / 10,000 = 9%`，不是两个百分比平均得到的 45%。

整体命中率只在所有请求正常完成、用量最终确认且数据有效、每个请求都完整提供输入与缓存字段时显示。没有模型请求、输入总量为零、缺字段，或者某次请求失败、取消、未完成，都显示 `--`。缓存超过输入等异常关系保留原信息并明确提示数据异常，不展示误导比例。

## 没上报，不代表没有消耗

有些兼容接口不提供缓存字段；流被取消时，最终 usage 也可能根本没有传回来。程序保留已经上报的数值，同时标记不完整请求。完全没有上报的字段显示未知，而不是把内部累计起点的零当成供应商测得的零。

比如两个请求中只有第一个上报完整用量，输入 2,000 token；第二个请求被取消且没有最终 usage。退出可以说“输入已上报 2,000，存在不完整请求”，不能说“本次精确消耗 2,000”，也不能据此算出完整缓存比。

上下文 token 估算回答的是“下一次发送可能占多少上下文”，不用于补齐历史账本；供应商账单也可能有另一个计费口径。退出小结不估算价格，更不把请求取消解释成免费。

## 恢复对话，服务仍需要重新启动

工作中停止本轮，明确转交 Session 的后台进程继续运行。退出整个应用则回收应用托管的全部进程，包括切换对话后留在其他 Session 的服务。关闭任务窗口只结束观察，不等于退出应用。

下次 `/session resume <UUID>` 恢复的是对话、计划、权限和保存的状态，不会按旧命令重新开服务器，也不凭旧 PID 接管一个系统进程。正常退出记录真实关闭结果；异常退出留下的活动记录，在重启恢复时标记失联。需要继续运行服务时，让模型或用户明确再次启动。

这些范围和进程收尾的具体细节见 [工具执行](tool-execution.md)。恢复输入队列时仍保持暂停，恢复对话本身不会自动执行排队消息或上一次未完成的工具。

## 可以复查的验证

[`test_exit_flow.py`](../../tests/tui/test_exit_flow.py) 覆盖确认窗口内外、恰好到期、继续操作、先停止后退出、重复停止和退出只能确认一次。纯状态测试不启动终端，不依赖定时睡眠。[`test_run_summary.py`](../../tests/tui/test_run_summary.py) 用真实 Session 存储检查当前与最近访问目标、删除后的回退、启动未使用历史，同时检查纯文本标题、完整 UUID、32 列输出以及缺失用量和清理失败文案。

界面验证还需要经过真实应用入口：在输入区和审批、任务、设置等页面检查停止与退出，在宽窄终端检查确认提示，等待后台进程真正关闭后再检查告别。用量验证则覆盖跨 Session、跨模型、压缩、多帧累计上报、缺字段与中断流。只看到漂亮的告别截图，不能证明清理和统计都已经正确完成。

[`test_tui_exit.py`](../../tests/tui/test_tui_exit.py) 覆盖宽窄终端、真实按键与弹窗焦点、手动压缩及其尚未开始的取消窗口。[`test_app_exit_integration.py`](../../tests/integration/test_app_exit_integration.py) 使用真实 `run_async` 入口和原生后台进程，模型响应由本地模拟协议提供；退出后检查进程已结束、会话写入锁可重新取得、告别只打印一次，用量与模型上报一致。

[`test_tui_exit_layout.py`](../../tests/tui/test_tui_exit_layout.py) 检查 32×16 终端中的后台进程提醒、Session 补全与暂停队列组合，以及确认解除后恢复原候选与草稿的行为。
