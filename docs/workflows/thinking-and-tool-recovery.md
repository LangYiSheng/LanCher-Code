# 思考协议、工具截断与会话恢复

一次工具调用失败，为什么会变成模型 API 报错？这个问题发生在两条信息链的交界处：给人看的聊天时间线，以及下一次请求真正发送的协议历史。

## 一次实际故障

模型准备通过 `write_file` 写一个完整网页。参数字符串有 16,818 个字符，最后停在 `<nav`，JSON 的字符串和对象都没有闭合。同次请求上报了 6,144 个输出 token，恰好与当时的默认思考额度 2,048 加正文额度 4,096 相同。这是旧版本的实际故障，不是当前默认额度。这支持“输出额度耗尽”的判断，但旧事件没有记录 `stop_reason`，因此不能把服务端的具体停止原因当作已记录事实。

旧处理把失败调用换成了一个虚构的解析器工具调用，再将整段网页放进错误返回。界面显示过的思考也没有进入协议历史。DeepSeek 收到这段工具历史后，要求补回 `content[].thinking`，请求随即失败。这个 Session 没有发生过上下文压缩。

## 给人看的思考，与需要回传的思考

`SessionMessage.trace` 是聊天时间线。它可以把流式文字合并成可折叠段落，记录等待、审批、执行和失败。时间线适合阅读，却不具备完整协议信息。

`ConversationMessage.blocks` 是请求历史。现在每次模型请求正常结束后，Provider 都会在 `message_end.assistant_blocks` 中交出完整的助手响应：思考、正文、工具调用，以及它们原本的顺序。TurnRunner 整段保存一次，而不是在工具分支只存调用、在最终分支只存正文。

Claude 兼容协议保存 `thinking` 的文字和 `signature`，也保存不可读的 `redacted_thinking.data`。签名可能由多个 `signature_delta` 分片组成，必须按顺序拼接；空文字加真实签名同样属于有效数据。OpenAI 兼容协议则保存原来的 `reasoning_content` 或 `reasoning` 字段来源，回传时使用同一字段。

这些内容不能从界面文字推导，也不能用空串、伪签名或累计思考段落代替。最终回答包含的思考同样保存；结束展示消息和接受工作中补充时，不再重复追加一份正文。

来源协议和模型会随完整助手响应保存。切换模型后，历史不能把旧模型的签名直接交给新模型。签名和密文也进入上下文估算与指纹：内容变化会使旧输入 usage 锚点失效，实际费用仍以提供方上报的 usage 为准。

## 思考显示与模型请求设置

`ui.show_thinking_status` 只控制界面是否显示思考轨迹，关闭后模型请求、推理能力和思考协议历史不变，工具活动也继续显示。模型是否推理、能否控制推理及其强度，由具体模型与端点决定；不能用一个通用“思考开关”概括所有深度思考模型。

模型推理设置使用 `reasoning_effort`，默认 `auto`。供应商发现得到的模型信息明确声明 adaptive 时自动启用自适应推理；仅声明旧版 enabled 时由应用分配接口额度。effort 范围及默认值读取端点声明，缺失字段保持未知；不根据型号、品牌或域名推断。详情见[模型发现](model-discovery.md)。

effort 调整速度与深度的取舍，不是硬 token 预算；所有推理输出都包含在 `max_output_tokens` 总额度内。旧 `thinking.enabled` / `thinking.budget_tokens` 读取时忽略、保存时移除。详细配置与具体模型支持范围见 [配置](../configuration.md#自动推理与-effort)。

## JSON 被截断时，怎样继续

`ToolCallAssembler.finalize_batch()` 先检查整个工具批次。遇到坏 JSON、非对象参数或明确的输出上限停止原因，本批工具都不执行。原本有效的同批调用也会收到“本批未执行”，避免模型误以为它已经产生了副作用。

每个调用仍使用提供方的真实编号和工具名。坏参数包装成 `{"INVALID_JSON": "原始参数"}`，只用于协议错误反馈，绝不交给工具执行器。随后用对应的真实调用编号逐个返回错误结果；结果说明 JSON 错误位置、没有执行，以及下一次应先用 `write_file` 写小型骨架，读取后用 `edit_file` 逐段填充。`write_file` 每次覆盖整文件，不支持追加，不能把多个片段依次覆盖写入。这样也无需把同一段大文件在输入和错误结果里重复放两遍。

缺失调用编号、工具名或出现重复编号时，程序停止当前轮次。没有真实身份，就无法可靠配对返回，不能再制造一个新调用来掩盖问题。

修复 JSON 结构不等于恢复文件内容。例如，给 `<nav` 后面补上引号和括号，仍然只得到半页 HTML。直接执行会覆盖目标文件。程序保存已收到的信息，让模型依据错误重新组织完整的小批操作；提示词也会提前要求大文件分段写入。

## 当前格式与跨来源历史

当前会话只接受事件格式 `3`。含工具调用或思考块的助手响应必须保存来源协议和模型，缺失来源或不符合当前协议块结构的数据会明确报错；旧文件原样保留，不再尝试补造思考、签名或来源。

切换协议或模型仍是受支持的运行时行为。`context/projection.py` 将来源不同且已配齐结果的工具交换转换为注明原因的文字历史；原请求与返回作为 JSON 引用，表示过去的事实，不成为本轮待执行调用。跨来源纯正文保留，原模型的思考签名不会发送给新模型。

投影只作用于请求副本，原始 transcript、事件日志和文件不改写。同一来源的完整响应按协议正常发送，即使响应没有 thinking 块也不被视为旧数据。尚未配齐结果的调用由中断恢复逻辑收尾，投影不把它伪装成已完成工作。

## 完整结束、输出上限与网络断流

`response_complete=True` 表示收到协议结束事件并拿到了完整快照。静默 EOF 会记作 `incomplete`，显式网络错误记作 `failed`。两者都不会自动重试，不执行未提交的工具，也不把半条助手协议响应保存成有效交换；界面已经收到的思考和部分正文继续保留，并显示明确错误。退出流时显式关闭生成器，让用量账本与网络资源完成收尾。

单次输出额度与上下文窗口是两个限制。普通请求缺省输出额度为 `32768` token，摘要为 `16384`；小窗口按比例适配。思考、正文和工具参数共用总输出额度，可在模型设置中独立配置 `max_output_tokens`，但仍须符合端点的支持上限。增大上下文窗口不会自动突破单次额度。

达到 `length`、`max_tokens` 或 `max_output_tokens` 时，即使还只有思考、没有工具调用，也进入额度耗尽处理。程序保留已收到的内容，在时间线显示警告并自动续接，不将它标成正常完成。Responses 的明确额度耗尽终态可能没有完整快照：这种情况只保存注明未完成的文字供续接参考，不回传半截工具参数或不完整思考签名。

额度耗尽自动续接默认最多 `3` 次，由 `runtime.output_continuation_limit` 配置。续接前重新检查上下文预算，接近输入软阈值时自动压缩，再发送后续请求。连续续接仍耗尽额度时，停止并明确提示“已有内容已保留，任务尚未完成”；一次正常响应会重置连续耗尽计数。普通 EOF、网络异常和供应商拒绝不进入这条续接路径。

额度耗尽响应中的工具批次仍整体不执行，不因为某个参数恰好合法就放行。完整身份可配对的调用收到逐个错误反馈，模型随后重新生成完整调用；身份也未完整时，只引用未完成事实，不伪造协议配对。自动续接不是自动执行或重放半截操作。

每次真实请求的用量账本保存 `stop_reason` 与实际发送的 `max_output_tokens`；额度耗尽记作 `incomplete`，不会仅因收到了结束帧就记为成功。完整助手历史也保存响应停止原因，恢复时可以区分正常完成与达到额度。提供方未上报的停止原因保持未知；已上报用量达到实际额度时，记录额度耗尽的判断。

消息时间线统一用持久提示显示警告、错误和停止状态，提示自己的 `severity` 不受整条消息最终状态影响。错误与停止不会覆盖已输出正文，提示不随思考区收起而消失；同一原因与文本去重，不丢不同事件的详细说明。提示和错误正文均正常渲染 Markdown，恢复会话后仍能查看。

## 验证与边界

真实 SSE 格式的离线集成测试覆盖多次工具循环、开始内容与增量混合、分片签名、不可读思考、最终回答、坏 JSON 整批拒绝、输出上限、静默 EOF、显式网络断流及 Session 恢复。测试还覆盖旧格式拒绝、当前格式跨模型历史的请求投影、思考计量及完整近期消息组的压缩保留。

部分原生 Claude 模型的签名还绑定原始请求前缀。仅保存完整块，不能保证改变系统提示、工具定义、早期历史或进行客户端压缩后签名仍有效。目前压缩保留完整近期消息组，不会伪造或修补签名；提供方对前缀的额外限制仍需独立的能力策略。本次 DeepSeek 修复的直接范围是完整思考回传、截断反馈和当前格式的跨来源投影。
