# 看懂一次上下文压缩

对话变长以后，模型每次请求都要携带越来越多的历史。压缩把较早的工作整理成摘要，保留近期交流和当前用户的原话，让下一次请求继续有空间。它改变的是发给模型的上下文；Session 中保存的原对话继续保留。

压缩值得看见。界面用一条可以展开的活动记录展示它，而不是让短暂通知消失后只剩一个更小的上下文数字。

## 一条记录，从开始到结束

手动 `/compact`、接近预算时的自动压缩，以及请求被供应商判断过长后的紧急压缩，使用同一套显示：

```text
▸ ◐ 正在压缩上下文（可能需要一段时间）

▸ ✓ 已压缩上下文
```

运行中的圆形图标转动，完成后变成勾。失败、停止和恢复时发现的中断分别显示自己的状态，不留一个永远转动的图标。这里没有进度百分比：一次摘要请求需要多久、还剩多少内容，客户端没有足够事实判断。

活动默认收起。点击标题，或者将焦点移到标题后按 Enter／Space，就能查看详情；相同操作收起。已经主动展开的记录在压缩完成、模型继续回答或整轮任务结束时保持展开，增量更新也不会重建它。运行中只展示已经知道的压缩前上下文、开始时间、耗时和触发方式；未产生的结果不占据几行 `--`。

成功时的详情例如：

```text
▾ ✓ 已压缩上下文
  上下文估算：≈48,000 → ≈12,000 tokens
  压缩率：75.0%（上下文减少比例）
  开始时间：2026-10-10 09:30:00
  耗时：12.4 秒
  触发方式：手动压缩
  压缩前计量：已校准估算
  压缩后计量：未校准估算
  以上为上下文估算。
  摘要请求的已上报用量另计。
```

压缩率是 `(压缩前 − 压缩后) / 压缩前`。它说明下一次请求的上下文估算减少了多少，不能解释成账单减少了 75%，也不能保证后续回答会缩短同样比例。供应商已经处理的输入不会因为压缩撤销；用于生成摘要的新请求还有自己的输入、输出与缓存用量，继续进入真实 usage 账本。

前后数字比较的是同一模型、系统提示和可见工具条件下的完整请求，不是只数聊天正文。压缩前若有有效 usage 锚点，会使用已校准估算；替换历史后旧锚点失效，压缩后先使用未校准估算。`≈` 和计量来源明确提醒读者：这些用于管理上下文的数字与供应商真实上报的消耗属于两个口径。未知保持未知，真实零仍然显示零；分母为零时不计算压缩率。详细算法见 [Token 与上下文](token-accounting.md)。

## 为什么它留在发生的位置

手动压缩没有一条新的用户消息，也不需要伪造一段助手回答。它独立放在已有聊天末尾；接下来发送的消息继续排在它后面。

自动和紧急压缩可能发生在一轮回答的中间。因此活动放进当前助手的时间线，与思考、工具和正文按发生顺序排列：

```text
LanCher
  先检查这几个文件。
  ▸ 已执行 3 个工具
  ▸ ✓ 已压缩上下文
  根据刚才的检查，接下来修改保存入口。
```

如果简单把活动追加到整个聊天区域末尾，模型的新正文仍会更新前面的助手控件，用户看到的顺序反而会颠倒。实现因此共用 `CompactionActivityWidget`，但为手动活动和轮内活动选择不同的挂载位置；轮内 trace 只引用活动 ID，状态和数字来自同一条活动记录。

活动更新沿用聊天的滚动规则：用户原本在底部才继续跟随，正在翻阅历史时不拉回。32 列终端的标题和数字可以自然换行；展开内容通过聊天主区滚动查看，输入区保留在原位置。spinner 只在运行期间启动计时器，终态和控件卸载都会停止它，刷新也不改变折叠选择。

## 重试、失败和恢复

一次压缩操作有一个稳定 ID。摘要请求过长时，内部可能调整输入并重试，但仍更新这一条活动记录。每次真实模型请求拥有自己的 request ID，并分别记入用量账本：界面只有一条活动，不代表只消耗了一次请求。

候选摘要必须通过结构、完成状态、输出上限和完整请求大小的检查，才会替换原上下文。失败或用户停止时，活动保留状态和原因；自动压缩失败但当前请求仍能继续时，详情会注明“本轮继续处理”。不能把失败当成压缩成功，也不能将尚未得到的压缩后数字显示出来。

### 提示词与格式容错分别负责什么

模型收到的是一份归档任务：系统提示提供完整九节模板，要求保留最新用户目标与约束、真实完成状态、未解决错误和下一步；没有相关信息写“无”，需要精确源码时提醒后续重新读取。历史末尾再加一条“现在只生成摘要”的专用指令，减少模型顺着旧对话继续回答的情况。这条指令计入请求预算，不保存进压缩后的对话。

模型偶尔会多写一句“以下是摘要”、包住代码围栏，或者省略外层 `<summary>`。这些包装差异可以在本地整理，无须再请求模型。客户端最终检查的是完整、唯一、有序且各有正文的九节摘要；代码示例里的 `##` 不冒充章节，行内代码或围栏里的 `<summary>` 字面量也不算第二份摘要。缺半边标签、多个摘要、缺节和空节继续拒绝。

如果结构仍不合格，最多重新生成一次：把具体格式错误告诉模型，从同一份历史重新总结，避免只依据坏摘要补造事实。两次请求仍属于同一条压缩活动，各自已上报的用量都会累计。第二次仍不合格就失败，不无限循环；未正常结束、输出达到上限、工具调用、网络错误和取消也不会被当成“修修格式就能用”的摘要。重试必须装得进预算，失败时原上下文继续保留。

取消时主动关闭正在消费的响应流，供应商连接和用量记录先收尾，压缩操作再返回。这样即使模型刚输出一小段文本时用户停止，界面退出或关闭 Session 也不会留下稍后才执行的用量回调。

有一种信息边界需要明确：摘要输入本身过长时，系统可能先省略最旧的完整历史组，才发出可容纳的摘要请求。`dropped_groups` 统计的是这种省略，不是“成功摘要了多少组”。详情因此显示：

```text
摘要输入省略：2 组旧历史（原对话保留）
```

这些组没有进入这次摘要请求，不能承诺新摘要仍包含其全部事实；原始对话仍在 Session 日志中。

活动保存到 Session，`/session resume` 后按原位置恢复结果和数字，默认收起。上次程序结束前仍处于运行中的活动恢复为“压缩已中断”，不会自动继续旧请求；实际结束时刻未知，耗时显示 `--`，不能用恢复时刻减去开始时刻充当工作时长。正常结束的记录使用真实结束时间，旧记录的耗时不会随着本次启动继续增长。展开状态属于当前界面的阅读选择，不影响模型上下文或已保存的压缩结果。

开始记录本身就能重建时间线中的活动引用：即使它刚写入、完整消息更新还未写入就退出，恢复时也能看见这次中断。成功时则把新上下文与完成指标放在同一条 `context.compacted` 事件中提交，避免界面说成功、实际历史却没有替换的情况。checkpoint 和完整日志重放遵循同一规则。

停止可能发生在 worker 尚未开始，甚至控件仍在挂载时。界面先登记工作状态，再挂载活动；准备期间的停止会终结同一 ID，随后不再启动摘要请求。保存异常也会停下图标、恢复输入，并明确提示写入失败；下次恢复仍以实际写入的日志为准。
